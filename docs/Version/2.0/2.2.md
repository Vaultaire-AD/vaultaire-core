## 🚧 Non publié

### 🔐 Quatre points critiques de l'audit du 25/09 *(TO-DO 95, 97, 99 et 100)*

**Un code à six chiffres à l'ouverture de session** *(point 95)*

- 🔐 **Le second facteur existe enfin là où l'on se connecte vraiment.** Il vivait sur le portail, au bind LDAP et pour les services du cluster — **pas** sur le canal qui ouvre les sessions des postes, c'est-à-dire le plus utilisé de tous. Un compte protégé par un second facteur dont le mot de passe fuitait était bloqué sur le portail et ouvrait une session SSH sur n'importe quelle machine - Lorens Viguie
- ⌨️ **Une invite après le mot de passe**, sur SSH, sur l'écran de connexion de Rocky et dans la tuile Windows. Un compte qui n'a pas de second facteur tape **`0000`** — c'est ce que dit l'invite, et c'est la seule valeur que le serveur accepte pour lui. Un vrai code envoyé pour un tel compte est refusé, pas ignoré : c'est le signe que quelque chose ne va pas - Lorens Viguie
- 🔑 **Une connexion SSH par clé sur un compte à second facteur est désormais refusée.** sshd n'ouvre pas de dialogue PAM dans ce cas : rien ne peut être demandé, donc rien n'est accordé. Pour qu'elle fonctionne avec un code, il faut `AuthenticationMethods publickey,keyboard-interactive` côté sshd — c'est documenté - Lorens Viguie
- 🚦 **`vlt mfa ducky on`** exige un code de tout agent. **Mettez le parc à jour avant** : une machine dont l'agent est trop ancien ne pourra plus ouvrir de session. `off` retire l'exigence en une commande, et l'activation est refusée tant que personne n'a enrôlé de second facteur. Les comptes qui en **ont** un doivent le fournir dans tous les cas - Lorens Viguie
- 🚫 **LDAP n'est pas concerné et ne le sera pas** : le protocole n'a pas de place pour un second facteur. Le code y reste accolé au mot de passe, comme avant - Lorens Viguie

**Le mot de passe d'installation ne fonctionne plus, et c'est voulu** *(point 99)*

- 🛑 **Le serveur refuse de démarrer sur la configuration livrée.** Elle portait un compte administrateur dont le mot de passe est **publié dans le dépôt Git du produit**, et qui entre dans le groupe aux pleins pouvoirs. Une installation faite depuis les fichiers du dépôt, sans les retoucher, exposait donc ce compte. Un avertissement aurait été lu une fois et oublié ; le refus arrive au moment où quelqu'un est devant l'écran et peut corriger - Lorens Viguie
- ⏳ **Les mots de passe posés par quelqu'un d'autre sont provisoires** : à la création d'un compte, à la réinitialisation par un administrateur, à l'installation. Celui qui l'a choisi le connaît — ce n'est donc pas encore un secret. Le titulaire est **averti à chaque connexion** et le remplace sur le portail ; passé 24 h, l'ancien cesse de fonctionner - Lorens Viguie
- 🖥️ **La session s'ouvre quand même, sur SSH comme sur Windows.** La refuser demanderait de changer son mot de passe sans pouvoir ouvrir de session pour le faire : quelqu'un dont le poste est la seule porte d'entrée serait enfermé dehors par la mesure censée le protéger. Le portail, lui, n'ouvre que la page de changement — c'est justement là qu'on le change - Lorens Viguie
- 📣 **Le message d'ouverture de session sert aussi au préavis d'expiration**, qui ne s'affichait jusqu'ici que sur le portail — c'est-à-dire là où l'utilisateur ne va pas. Une seule ligne, quelle qu'en soit la cause - Lorens Viguie
- 🐛 **Un défaut trouvé en chemin** : le fichier livré écrivait `administreur`, le programme lisait `administrateur`. **Toute la section était ignorée en silence** depuis toujours, et changer le mot de passe dans le fichier n'avait aucun effet. C'est corrigé, et le serveur refuse maintenant de démarrer sur l'ancienne orthographe **en la nommant** - Lorens Viguie

**Un utilisateur ne devient plus root avec un lien symbolique** *(point 97)*

- 🛡️ **Un poste ne se prend plus par son dossier personnel.** Les politiques du périmètre utilisateur sont appliquées **par root**, à chaque ouverture de session, dans un dossier que l'utilisateur contrôle. Il lui suffisait de remplacer un répertoire par un lien vers `/etc` pour que `/etc` lui soit attribué — après quoi il réécrivait `/etc/shadow` et devenait administrateur de sa machine - Lorens Viguie
- 🧭 **La traversée ne suit plus aucun lien** : chaque niveau du chemin est ouvert à partir du précédent, et le fichier est écrit sans jamais repasser par son chemin. C'est la seule garantie qui tienne — entre une vérification et une écriture, l'utilisateur peut avoir tout remplacé - Lorens Viguie
- 🚨 **Un chemin suspect est signalé, pas confondu avec une panne.** Le module est abandonné et une ligne de sécurité nomme le compte : c'est le signe qu'un poste a été préparé par quelqu'un qui savait quelle politique il allait emprunter - Lorens Viguie
- 🔍 Au passage : **la surveillance de dérive lisait, elle aussi, à travers les liens**. Un lien posé à la place d'un fichier déployé est désormais une dérive — ce qui est d'ailleurs plus juste - Lorens Viguie
- ✅ **Rien n'est retiré aux GPO** : les chemins autorisés ne changent pas, et une politique peut toujours écrire la configuration SSH, les fichiers d'un dossier personnel ou une unité systemd - Lorens Viguie

**`1234` n'est plus un mot de passe acceptable** *(point 100)*

- 🔑 **Douze caractères minimum** pour tout mot de passe neuf, avec un **plancher de huit qui ne se désactive pas**. Il n'y avait aucune règle : le portail acceptait n'importe quelle chaîne non vide. Le hachage du produit protège d'une base volée ; il ne fait rien contre quelqu'un qui essaie des mots de passe, et le freinage ne verrouille jamais - Lorens Viguie
- 📝 **Aucune règle de complexité**, volontairement : elle produit `Password1!`, qui figure dans toutes les listes, et pousse à écrire le mot de passe sur un papier. **Une phrase de passe est ce qu'on veut encourager.** C'est aussi la recommandation de l'ANSSI et du NIST - Lorens Viguie
- 🚫 Sont refusés : l'identifiant du compte, son domaine, le nom du produit et les classiques — comparés après normalisation, `P@ssw0rd` valant `password`. Et **le refus dit ce qui manque**, pas « mot de passe invalide » : un refus muet fait essayer des variantes au hasard, donc finir sur quelque chose d'à peine acceptable - Lorens Viguie
- ⏱️ La règle ne touche **pas** les mots de passe déjà en place : on ne peut pas recalculer ce qu'on refuserait, ils n'existent nulle part en clair. Le parc s'y conforme au premier changement de chacun - Lorens Viguie
- 🔒 Le contrôle est adossé au **hachage**, pas recopié dans chaque écran : un chemin de création écrit plus tard sera couvert sans que personne n'y pense. C'était exactement le défaut - Lorens Viguie

### 🛡️ Quatre points de l'audit du 25/09 *(TO-DO 96, 106, 107 et 108)*

**Le domaine du groupe superadmin est fermé en écriture** *(point 96)*

- 🛡️ **Le groupe `vaultaire` ne s'atteint plus par le domaine.** Ce groupe porte tous les droits sur tous les domaines, et il est rattaché à un domaine comme n'importe quel groupe : un délégué qui pouvait ajouter des comptes sur `fr` s'ajoutait lui-même au groupe `vaultaire` et devenait superadmin - Lorens Viguie
- 🔒 La protection est posée sur le **domaine** et non sur la commande, parce qu'il y avait plusieurs chemins — y créer un groupe, y rattacher une permission, y déplacer une machine — et qu'une liste de commandes à compléter aurait oublié la prochaine. Elle couvre le domaine **et tous ses sous-domaines** : « protégé dans son intégralité » n'aurait aucun sens si l'on pouvait créer `x.vaultaire.fr` pour y travailler librement - Lorens Viguie
- ✅ **Ajouter quelqu'un au groupe `vaultaire` reste possible** — c'est le geste normal pour confier l'administration. Il est réservé aux membres de ce groupe : celui qui donne le pouvoir doit déjà l'avoir. Voir n'est pas écrire : la lecture ne change pas - Lorens Viguie
- 🌍 **Le domaine protégé est lu dans la base**, pas écrit en dur : un annuaire qui rattache son groupe superadmin à autre chose est protégé sur **son** domaine. En cas de panne de lecture, on protège quand même `vaultaire.fr` plutôt que de n'en protéger aucun - Lorens Viguie

**Le compte d'amorçage n'ouvre la session de personne** *(point 106)*

- 🚪 **`ssh vaultaire@une-machine` est refusé**, ainsi que la vérification de ce compte par un service. `vaultaire` désigne deux choses — le compte sous lequel **chaque machine du parc** ouvre son tunnel, et le compte du groupe superadmin — et c'est la même ligne de l'annuaire - Lorens Viguie
- 🔌 **Le tunnel machine n'est pas touché** : c'est la même session, et la refuser couperait le parc. Ce qui est fermé est l'ouverture d'une session **de personne** sous ce nom. Le portail reste ouvert à ce compte : c'est le compte de secours - Lorens Viguie
- 🧪 Ce qui protégeait déjà le produit — aucun droit ne se déduit du nom d'une session Ducky — **n'était écrit nulle part**. Un test le vérifie désormais sur l'ensemble du code réseau, et échouera le jour où quelqu'un écrira cette lecture : c'est le genre de défaut qu'aucun test de comportement n'aurait vu - Lorens Viguie

**Une machine n'apparaît plus deux fois dans `status -c`** *(point 107)*

- 🔁 **L'unicité « un compte, une machine » est désormais tenue par la base**, comme elle l'est déjà pour les sessions PAM. Elle ne l'était que par le code, en deux endroits : deux authentifications simultanées de la même machine créaient chacune leur ligne - Lorens Viguie
- 🐛 Ce n'était pas théorique : le `--fetch-key` de sshd ouvre une session à **chaque connexion SSH**, en parallèle du tunnel permanent. La fenêtre s'ouvrait en fonctionnement normal, sans que personne ne cherche à la provoquer — d'où un doublon intermittent, difficile à imputer - Lorens Viguie
- 🧹 Les bases existantes sont **dédoublonnées au démarrage** avant la pose de la contrainte, et le nombre de lignes retirées est journalisé. Un core qui ne peut pas poser l'index continue de servir - Lorens Viguie

**Un proxy remonte enfin ce qu'il relaie** *(point 108)*

- 📈 **`vlt cluster list` porte deux colonnes neuves** : RELAIS (connexions en cours / relayées depuis le démarrage, et celles qui ne sont pas passées) et TRAFIC. La page **Admin → Cluster** les montre aussi, et la fiche d'un nœud donne le détail **par relais** — l'agrégat dit qu'un proxy écarte des connexions, seul le détail dit lequel de ses relais - Lorens Viguie
- 🕳️ **La trame existait des deux côtés depuis longtemps, et personne ne l'émettait.** Le serveur l'acceptait, la plafonnait, purgeait sa table au bout de trente jours et exposait un réglage de rétention : tout cela tournait à vide. Une supervision qui affiche une table vide se lit « aucune charge » alors qu'elle dit « aucune mesure » - Lorens Viguie
- ⚠️ **Correction d'une affirmation fausse dans la documentation** : il y était écrit que ces mesures ordonnent la liste des nœuds servie aux agents. Ce n'est pas le cas, et ce ne sera pas le cas ici : un nœud choisit les chiffres qu'il déclare, et l'acheminement du parc ne doit pas en dépendre. L'ordre reste celui de l'affinité, de la priorité et de l'état - Lorens Viguie
- ⏱️ Une mesure de plus de **trois minutes** n'est pas affichée : un compteur de connexions en cours périmé se lirait comme l'état courant. Une seule ligne part par battement plutôt qu'une par compteur — six auraient rempli la table d'un million de lignes par proxy - Lorens Viguie

### 🔏 Les politiques GPO sont signées par le cluster *(TO-DO 52)*

- 🔏 **Une GPO porte désormais sa preuve avec elle.** Le cluster signe chaque livraison avec une clé qui lui est propre, et l'agent la vérifie avant d'appliquer quoi que ce soit. La signature lie la politique à **sa machine** : celle d'un poste ne peut pas être resservie à un autre - Lorens Viguie
- 🔑 **Cette clé n'est pas celle du tunnel, et c'est tout l'intérêt.** La confiance de transport peut s'étendre en cours de route — un core de confiance peut en annoncer d'autres — alors que la clé de signature est posée à l'installation et ne s'apprend jamais. Un nœud entré par ce chemin peut parler à un agent, pas lui faire appliquer une politique - Lorens Viguie
- 🚦 **`vlt gpo signature on`** fait refuser les politiques non signées. Les machines installées avant la 2.2 n'ont pas la clé : elles continuent d'appliquer sans vérifier, donc **activer l'exigence ne casse rien** sur un parc ancien. L'exigence est poussée par le core, et se retire de la même façon — une migration dont on ne peut pas sortir n'est pas une migration - Lorens Viguie
- ⚠️ Écrit noir sur blanc dans la documentation : un core dont la **base** est compromise détient cette clé. La signature protège le document, pas le core - Lorens Viguie

### 📈 « Depuis quand cette machine échoue ? » *(TO-DO 53)*

- 📈 **`vlt gpo status <machine>` répond enfin à la question qui suit un « partial ».** Une nouvelle section montre les changements d'état d'application, le plus récent en tête. C'est un historique des **changements**, pas un journal des cycles : une machine saine n'y produit qu'une ligne, à son premier rapport - Lorens Viguie
- 🗑️ Conservation réglable (`gpo_history_retention_days`, 90 jours), purgée à la cadence des journaux. L'état courant, lui, n'est jamais purgé - Lorens Viguie
- 🔗 **La fiche d'une machine renvoie à sa conformité** : elle ne portait aucun lien GPO, alors que c'est la première chose qu'on y cherche - Lorens Viguie

### 🧹 Le ménage des comptes locaux fonctionne enfin *(TO-DO 70)*

- 🧹 **Les comptes du domaine restés quatre jours sans connexion sont de nouveau retirés.** La tâche cherchait dans le champ commentaire de `/etc/passwd` une marque que rien n'écrivait : elle ne trouvait **aucun** compte, tous les jours, depuis toujours. Elle s'appuie maintenant sur la carte des UID, qui est la liste de ce que l'agent a réellement créé - Lorens Viguie
- 📅 Et elle ne tournait qu'**un jour sur deux** : la boucle dormait vingt-quatre heures de plus après avoir travaillé - Lorens Viguie
- 🌍 **`lastlog` est lu en locale C.** Sur une machine en français, la date ne s'analysait pas et le compte passait pour actif pour toujours - Lorens Viguie
- 🛟 Un `/etc/passwd` illisible **n'arrête plus l'agent entier** — donc l'authentification de toute la machine — pour un fichier qu'il n'avait qu'à relire au tour suivant. Et l'UID d'un compte supprimé est enfin rendu : rien ne retirait son entrée de la carte - Lorens Viguie


### 🏠 La dérive des GPO utilisateur est enfin surveillée *(TO-DO 33)*

- 🏠 **Ce qu'une GPO pose dans un `HOME` est désormais vérifié**, à l'ouverture de session. C'était le scope où la dérive est la plus probable — le `HOME` est le seul endroit où quelqu'un écrit librement sans être root — et le seul qui n'était jamais scanné : un fichier modifié ou supprimé y restait indéfiniment sur un parc stable - Lorens Viguie
- 🔁 **La correction arrive avant le shell.** Le scan précède le cycle utilisateur, comme côté machine : l'environnement est remis en état avant que la session ne soit accordée, et non à la connexion d'après - Lorens Viguie
- ⏱️ **Une vérification par cadence GPO et par compte**, et non une par authentification : PAM est sollicité à chaque `ssh` mais aussi à chaque `sudo`, et scanner à chaque passage aurait envoyé un rapport de conformité par commande privilégiée - Lorens Viguie
- 🔒 **Le cycle utilisateur est sérialisé par compte** : deux connexions simultanées — deux terminaux, ou un `sudo` pendant une session `ssh` — travaillaient en parallèle sur le même `HOME` et le même état local - Lorens Viguie
- 📊 `vlt gpo status <machine>` affiche maintenant une conformité par utilisateur, là où il disait « jamais vérifiée ». Rien n'a changé côté core : la trame `05_15` portait déjà le nom du compte, et les tables aussi - Lorens Viguie
- ⚠️ Assumé et écrit : une seconde connexion pendant qu'une première travaille peut réécrire un fichier que la personne vient d'éditer. Un parc où ces interventions sont légitimes met les GPO concernées en **audit** - Lorens Viguie


### 🔀 Les machines suivent le cluster, et basculent sur le bon nœud *(TO-DO 90, et 84 refermé)*

- 🔄 **La liste des cores et proxies ne se met plus à jour qu'au démarrage.** Chaque machine la redemande toutes les **30 minutes** — cadence réglable depuis le core (`node_list_refresh_minutes`), comme celles des groupes et des GPO. Un nœud ajouté, retiré ou repriorisé est pris en compte sans redémarrer quoi que ce soit - Lorens Viguie
- ⚡ **`vlt cluster refresh <machine> | -g <groupe> | --all`** demande l'actualisation tout de suite, au lieu d'attendre le prochain tour. Une machine hors ligne n'est pas une erreur : elle relira sa liste à sa reconnexion. Le droit est celui de la machine (`write:update:client`), pas celui du cluster : un délégué rafraîchit ses postes, et seulement les siens - Lorens Viguie
- 🔀 **Un poste ne reste plus accroché à un nœud de secours.** Si le nœud qu'il utilise n'est plus le mieux placé, il rouvre son tunnel sur celui qui l'est. **À priorité égale il ne bouge pas** — basculer entre deux nœuds équivalents ne gagne rien et coûterait une coupure à chaque tour - Lorens Viguie
- 🐛 Trouvé en chemin : l'abonnement aux nouvelles listes n'admettait qu'**un** destinataire, et le suivant écrasait le précédent. Brancher la bascule aurait désarmé en silence la persistance de la liste apprise (2.2, TO-DO 61) - Lorens Viguie
- ✅ **TO-DO 84 refermé** : les cores qui ne réintégraient pas le cluster après une veille de l'hôte. C'était bien la purge à cinq minutes, corrigée au point 85 - Lorens Viguie

### 🔑 Un core redémarre sur sa propre base *(TO-DO 94)*

- 🐛 **Un core installé ailleurs que dans `/opt/vaultaire/` ne repartait pas sur sa base** : au second démarrage, il s'arrêtait sur « certificat `server_login_client` existe déjà ». Les fichiers de clé étaient écrits sous un chemin codé en dur pendant que le répertoire suivait la configuration - Lorens Viguie
- 🔐 Plus grave, et corrigé avec : l'amorçage prenait **toute** erreur pour « la clé n'existe pas encore » et régénérait. Cette clé est celle que `create -c … --join` dépose sur les machines : la régénérer aurait invalidé l'accès à tout ce qui l'avait déjà acceptée. Seule une clé **absente de la base** autorise désormais une génération - Lorens Viguie

### 🗺️ Les réglages d'un nœud ne se perdent plus *(TO-DO 85)*

- 💾 **L'adresse publique, le port exposé, la priorité et l'affinité d'un nœud survivent à son absence.** Un nœud muet plus de cinq minutes — redémarrage lent, veille, coupure — était supprimé, puis revenait vierge. Il passe désormais hors ligne et garde ses réglages ; il n'est oublié qu'après le délai de purge (`cluster purge-delay`, 24 h) - Lorens Viguie
- 🔁 **Un core dont la ligne a disparu se réenregistre seul**, au lieu de demander un redémarrage — c'est probablement ce qui empêchait les cores de revenir après une veille - Lorens Viguie
- 📋 **Page Cluster** : une liste courte, et la fiche d'un nœud s'ouvre au clic, au lieu de tous les formulaires dépliés les uns sous les autres - Lorens Viguie
- 🧹 Le délai de purge des services est enfin respecté : ils étaient supprimés au bout de cinq minutes, eux aussi - Lorens Viguie

### 🔄 « gpo refresh » atteint enfin la machine connectée *(TO-DO 89)*

- 🔄 **`gpo refresh` ne répond plus « hors ligne » à une machine connectée.** La demande partait vers une session prise au hasard parmi celles du poste — parfois une connexion pas encore authentifiée, parfois celle d'un utilisateur. Elle vise désormais le tunnel de la machine - Lorens Viguie
- 💬 La commande distingue **hors ligne** de **connectée mais demande non remise**, avec l'erreur : dans le second cas, il ne sert à rien d'attendre une reconnexion - Lorens Viguie
- 🚫 **Les ordres de révocation** poussés aux machines connectées profitent de la même correction : un kill switch pouvait rester en attente sur un poste pourtant en ligne - Lorens Viguie

### 🔀 Le proxy relaie aussi HTTPS et LDAPS *(TO-DO 72)*

- 📦 **Un site installe ses paquets depuis un Nexus en ne joignant que son proxy** : relais `https`, cibles demandées au core — les Nexus en ligne, dans l'ordre de leur priorité. TLS reste de bout en bout : le proxy ne voit aucun paquet - Lorens Viguie
- 📇 **Les applications d'un site interrogent l'annuaire par le proxy local** : relais `ldaps`. Le core reçoit l'adresse **réelle** du client, et le freinage des mots de passe erronés compte par machine, pas par site - Lorens Viguie
- 🔒 Cette adresse n'est crue que d'un **proxy enregistré** ; de n'importe qui d'autre, la connexion est fermée et tracée. LDAP en clair reste **refusé** : relayé, il ferait voyager les mots de passe en clair jusqu'au core - Lorens Viguie

### 📦 Une seule version de chaque dépendance *(TO-DO 93)*

- 🔐 **`golang.org/x/crypto` en une seule version (v0.54.0) dans tout le produit** — la bibliothèque qui porte argon2id, ed25519 et le client SSH. Un correctif de sécurité protège désormais tous les modules à la fois - Lorens Viguie
- 🧹 **`go-ldap` retirée du core**, où plus rien ne l'importait, avec les deux bibliothèques qu'elle tirait pour rien - Lorens Viguie
- 📄 **YAML v3 partout** : le core et l'agent lisent désormais leurs fichiers avec la même bibliothèque. ⚠️ Une clé écrite **deux fois** dans un fichier de configuration retouché à la main est maintenant refusée, avec sa ligne, au lieu d'être écrasée en silence - Lorens Viguie

### 📜 Un seul journal pour tous les cores *(TO-DO 91)*

- 📜 **Les cores écrivent leur journal dans une même table de la base**, chaque ligne signée du core qui l'a émise. Plus besoin de deviner quel core a traité une requête avant de pouvoir lire quoi que ce soit : `vlt logs` et **Admin → Logs** montrent tout le cluster - Lorens Viguie
- 🔎 **Filtres par gravité, core, code et période, et pagination** — sur le portail comme en ligne de commande, par la même action. `logs --level WARNING --since 2h` répond à la question qu'on pose devant un incident - Lorens Viguie
- 🗑️ **Conservation réglable** : `log_retention_days` (30 jours par défaut), purge au démarrage de chaque core puis toutes les 24 h (`log_purge_hours`). Une table de journaux sans borne remplirait le disque de la base — et emporterait l'annuaire avec elle - Lorens Viguie
- 🛟 **Base injoignable : le journal le dit** et montre à la place la mémoire du core qui répond, lui seul. Un core qui n'arrive plus à écrire en base garde ses lignes sur sa sortie standard et signale une fois par minute combien en manquent (`VLT-LOG001`) - Lorens Viguie
- ℹ️ Le niveau DEBUG ne part **pas** en base : il reste sur la sortie standard du core, qui reste complète - Lorens Viguie

### 🔑 Une session utilisateur n'est plus une machine, et Windows dit pourquoi il refuse *(TO-DO 92 et 83)*

- 👥 **`status -u` et `status -c` lisent désormais deux tables distinctes.** Une session ouverte par PAM n'apparaît plus comme une machine connectée : un poste avec trois personnes dessus reste **une** ligne dans `status -c`. C'était une régression de la version précédente, corrigée avant publication - Lorens Viguie
- 🗄️ La nouvelle table porte l'unicité `(compte, machine)` **en base**, là où celle des sessions Ducky ne l'avait que dans le code. Aucune migration : les lignes en trop expirent d'elles-mêmes, plus rien ne les prolongeant - Lorens Viguie
- 🚫 **Une révocation retire aussi les sessions affichées** : un tableau de bord qui montre encore comme connecté un compte qu'on vient de couper est un tableau de bord qui ment — et c'est au moment d'un kill switch qu'on le regarde - Lorens Viguie
- 🪟 **Windows : « code 2245 » devient une phrase.** C'est la politique de mot de passe **du poste** qui refuse le mot de passe du domaine — longueur, complexité, ou mot de passe encore dans l'historique, le nom du code n'en désignant qu'une. Le compte local doit porter le mot de passe que la personne tape : l'agent ne peut pas en choisir un autre - Lorens Viguie
- 🔧 `install.ps1` affiche la politique locale et **propose** de l'aligner, en annonçant ce qu'il change. Rien n'est assoupli sans accord : la robustesse devient celle de la politique de **domaine**, qui est ce qui protège réellement le compte - Lorens Viguie

### 🩹 Trois défauts de la recette du 24/09 *(TO-DO 81, 87 et 88)*

- 🪟 **Encodage du poste Windows** : deux défauts inverses. Les scripts d'installation partent désormais **avec** une marque d'ordre des octets — sans elle, Windows PowerShell 5.1 lit le fichier en ANSI et tous les accents deviennent des `Ã©` — et ce qu'ils **écrivent** part **sans**, la norme JSON l'interdisant. - 📄 L'agent tolère par ailleurs une marque en tête de `client_conf.json` : le fichier sera rouvert dans le Bloc-notes pour ajouter un core, et refuser une configuration valide pour trois octets invisibles serait une mauvaise manière de faire respecter la norme - Lorens Viguie
- 🔐 **`trusted_ca` reconnaît la distribution à sa commande**, plus à un répertoire. `/usr/local/share/ca-certificates` est un répertoire ordinaire que n'importe quel paquet peut créer : une Rocky 9 était prise pour une Debian, et l'agent lançait `update-ca-certificates`, qui n'y existe pas. Un magasin n'est utilisable que si le programme qui le **compile** est là - Lorens Viguie

### 👥 `status -u` montre enfin qui est connecté, et où *(TO-DO 68)*

- 👥 **Une session ouverte par PAM apparaît dans `vlt status -u`.** Depuis la suppression du défi, l'authentification d'une personne passe dans le tunnel de la machine : aucune ligne n'était écrite, et la commande ne listait que le compte `vaultaire`, une fois par machine. Le core savait qui il venait de laisser entrer et l'oubliait dans la seconde - Lorens Viguie
- 🖥️ **Nouvelle colonne MACHINE** : une personne connectée sur trois postes donne trois lignes. Une session, c'est qui *et* où - Lorens Viguie
- 🚪 **Une déconnexion se voit** : la fermeture PAM envoie une trame `03_11` qui efface la ligne — et **ne ferme aucune connexion**, contrairement au `02_05` qui coupait autrefois le tunnel de toute la machine. Un agent ne peut fermer que des sessions ouvertes chez lui : la machine vient de l'en-tête authentifié, jamais du contenu - Lorens Viguie
- ⏲️ **Le battement de la machine prolonge les sessions de ses utilisateurs** — elles n'en ont pas à elles. Une machine éteinte voit donc les siennes expirer en dix minutes. ⚠️ Un poste **Windows** n'émet pas la trame de fin : ses sessions restent affichées jusqu'à l'extinction (TO-DO 79) - Lorens Viguie

### ⏱️ Les GPO se rafraîchissent quand on le décide *(TO-DO 50 et 51)*

- ⏱️ **La cadence de rafraîchissement des GPO devient un réglage du core** — `settings set gpo_refresh_minutes 10` — au lieu d'une constante d'une heure compilée dans l'agent. La valeur voyage avec les réponses GPO : chaque machine l'applique à son cycle suivant, sans redémarrage d'agent ni de core - Lorens Viguie
- 🩺 Au passage, la colonne **SUIVI** de `gpo status` cesse de mentir : « en retard » vaut trois cycles **réels** et non trois heures figées. Le core portait une seconde copie de la durée, qu'il fallait tenir d'accord avec celle de l'agent - Lorens Viguie
- ⚡ **`vlt gpo refresh <machine>` et `vlt gpo refresh --all`** : l'équivalent de `gpupdate /force`. La machine repart sur son cycle ordinaire — rien n'est appliqué par un chemin différent. Une machine hors ligne rafraîchira à sa reconnexion ; rien n'est mis en file. Le droit exigé est `write:update:client` sur la machine, et non `write:update:gpo` : ce qu'on engage est le poste, pas la politique - Lorens Viguie
- 🔌 **Un tunnel rétabli déclenche un cycle**, et **un cycle en échec est retenté plus tôt** (dégressivité plafonnée à la cadence). Une machine coupée deux heures revenait jusqu'ici avec la politique de la veille jusqu'au tour suivant - Lorens Viguie

### 🔐 Seize remarques de recette : domaines, RBAC, LDAP, tunnel, formation *(TO-DO 55 à 66)*

- ⚠️ **Connexion aux machines : seulement sous ses domaines principaux.** Le domaine tapé (`alice@test.fr`) doit être le domaine principal — les deux derniers labels — d'un groupe du compte. Un compte `auth` partout se connectait sous n'importe quel domaine existant, et `03_06` (clés pour sshd) ne vérifiait pas le domaine. Les comptes locaux créés sous un sous-domaine (`user@infra.acme.lan`) ne se reconnectent plus sous ce nom - Lorens Viguie
- 🌳 **Les domaines parents sont créés avec le groupe** (`create -g Web web.cloud.acme.lan` crée `acme.lan` et `cloud.acme.lan` s'ils manquent), rattrapés au démarrage sur une base existante ; le dernier groupe d'un domaine qui a des sous-domaines ne se supprime plus - Lorens Viguie
- 🔑 **Détacher n'est plus supprimer.** Nouveau verbe RBAC `remove` (colonne « Détacher ») : retirer un compte, une machine, une permission ou une GPO d'un groupe exige `write:remove:<objet>`, et non plus `write:delete:<objet>`. Migration unique : chaque droit `delete` est recopié en `remove`, portée comprise - Lorens Viguie
- 👁️ **L'arborescence web respecte le périmètre** (elle montrait tout l'annuaire, comptes compris, à qui détenait `write:eyes`) ; `eyes -g <domaine>` filtre les sous-domaines ; **la page Cluster exige `read:cluster`** - Lorens Viguie
- ⚠️ **LDAP et second facteur** : un compte MFA se lie avec son mot de passe **suivi** du code ; `ldap.mfa_bypass: true` rétablit le mot de passe seul, en le journalisant. LDAP contournait le second facteur par défaut. Une application liée avec un compte MFA est refusée à la mise à jour - Lorens Viguie
- 🔌 **Une déconnexion ne coupe plus le tunnel machine.** La fermeture PAM visait le tunnel `vaultaire` ; le `--fetch-key` de sshd effaçait la présence de la machine dans `status -c` ; et une seule session expirée effaçait **tout le parc** de `status -c` (toutes les machines sont connectées sous `vaultaire`). Le tunnel est ouvert au démarrage sur tout nœud, supervisé et relancé après panique ; le battement recrée la présence - Lorens Viguie
- 🌐 **GPO `dns_resolver` sur Rocky 9** : passe par NetworkManager (`[global-dns]`) quand systemd-resolved n'est pas actif, ou écrit `/etc/resolv.conf` ; plus aucun service démarré par effet de bord - Lorens Viguie
- 🎨 Les erreurs du portail s'affichent en rouge (huit pages les montraient en vert) - Lorens Viguie
- 🎓 **Formation** : `vaultaire` / `password` n'a jamais ouvert le portail — le jalon 1.3 se connecte avec `admin` et **donne** un mot de passe à `vaultaire` ; le jalon 3.2 fait couvrir l'IP de l'hôte par le certificat de l'API (sinon `vlt` échoue en x509), et l'alias passe en `docker exec -i` - Lorens Viguie
