## 2. Le détail

### 2.1 § 7e — relevés demandés au TO-DO 220

- `essai_audit` (audit) : `file_deploy` `/etc/vlt-recette-audit.conf` ;
  `essai_enforce` (enforce) : `file_deploy` `/etc/vlt-recette-enforce.conf` ;
  toutes deux sur `Infra`.
- À la politique reçue : `GPO: machine — 1 module(s) sur 2 en audit (signalés,
  jamais corrigés) : file_deploy:/etc/vlt-recette-audit.conf ; les autres en
  enforce`.
- Les deux fichiers cassés, cycle suivant : `GPO: mode audit, 1 module(s) en
  ecart signale(s) sans correction : [file_deploy:/etc/vlt-recette-audit.conf]`,
  `GPO: 1 module(s) marque(s) pour reapplication au prochain cycle :
  [file_deploy:/etc/vlt-recette-enforce.conf]`, puis le fichier enforce
  réécrit. `vlt gpo status` : un écart, l'audit, « signalé, non corrigé ».
- Rapport de debug : `dont 1 en mode audit (écart signalé, jamais corrigé) :
  file_deploy:/etc/vlt-recette-audit.conf`.
- Le cas « attente partagée » ne se monte pas avec deux modules identiques :
  deux `systemd_service` `chronyd` / `started`, un par GPO, et le core refuse
  **toute** la politique machine (`resolve_conflict`) — plus rien n'est appliqué,
  pas même la GPO en enforce. À trancher : TO-DO **222**.

Les modules ont été posés en base (le portail demandait un mot de passe
d'administrateur), avec `BumpVersion` ; le core les a relus et livrés comme
les autres.

### 2.2 § 81 — SELinux sur Rocky 10

1. `install.sh` (1.1.0) : compile et installe, mais dit l'agent « arrêté » (il
   tournait : `ps` tronque son nom en `vaultaire_clien`) et « résolution dans le
   contexte sshd_t : ÉCHOUE » — `runcon -t sshd_t` est refusé à root sur Rocky
   10 (« contexte incorrect »), ce qui ne dit rien de la politique.
2. Une vraie connexion de `bob.recette@acme.lan` : refusée. `semodule -DB`
   montre ce que des `dontaudit` cachaient : `sshd_session_t` (le domaine de
   `sshd-session`, OpenSSH ≥ 9.8) ne peut pas exécuter `vaultaire_exec_t`
   (`AuthorizedKeysCommand … Permission denied`, status 127) ; une fois la clé
   passée, il ne peut ni lire `shadow_t` ni lancer `chpasswd` (`passwd_exec_t`) :
   « chpasswd failed », mot de passe refusé.
3. Politique **1.2.0** (DO 228) : transition vers `vaultaire_t` pour
   `--fetch-key`, et pour `sshd_session_t` les droits de `sshd_t` (dans un
   `optional_policy`). `install.sh` vérifie désormais par une connexion
   locale. Résultat : connexion clé + mot de passe + code en enforcing ;
   `chcon bin_t` → refusé (« PAM: Authentication service cannot retrieve
   authentication info ») ; `setsebool vaultaire_agent_non_confine on` →
   rétabli ; `--remove` puis réinstallation : OK.
4. `collect.sh --agent` : la liste brute est au TO-DO **180**.

À rejouer : Rocky 9 et Debian 13 avec la 1.2.0 ; la réinstallation par
`-join`.

### 2.3 Proxy : § 22b, § 99, § 101

Le proxy de la pile `deployments/pre-prod/vlt-proxy` n'ouvrait pas son relais
Ducky au bon port (`command: -listen-port 8443` dans le compose) : corrigé (DO
**230**), image reconstruite. Le proxy relancé, la révision gardée par le core
était refusée : `set ducky --ecoute :6666` a remis d'accord (TO-DO **226**).

**Le défaut qui compte (TO-DO 225).** Le relais vise d'abord l'adresse
**exposée** du core, celle des agents (`192.168.30.3`). Depuis le conteneur, elle
repasse par le NAT de l'hôte : le core voit `172.18.0.1`, pas le proxy
(`172.18.0.5`). Conséquences :

- LDAPS relayé : « en-tête PROXY reçu d'un pair qui n'est pas un proxy
  enregistré (172.18.0.1) » ;
- purge : « 0 machine(s) prévenue(s) », le poste reste par le proxy — c'est le
  NON du 25/10, sous une autre cause que celle corrigée au 216.

Avec le contournement (`--source liste --adresses vaultaire-ad:<port>` pour
`ducky` et `ldaps`), tout passe :

| § | Ce qui a été vu |
|---|---|
| 22b | Keycloak « Test connection / authentication » par `ldaps://vlt-proxy-recette:1636` ; le core : `ouverte LDAPS depuis 172.18.0.2 … via le proxy 172.18.0.5` |
| 99 | purge hors maintenance refusée ; en maintenance : « liste redemandée hors tour (maintenance du proxy …) », « nœud à quitter, placé en dernier pendant 15m0s », reconnexion en 15 s sur le core en rotation `out` ; rapport de debug « à quitter (maintenance) » ; core « 1 machine(s) prévenue(s) » ; `online · maint. (purge)` |
| 101 | bind par le relais attribué au poste (`depuis 192.168.30.8 … via le proxy`) ; en-tête PROXY v2 envoyé au core par le poste : refusé et journalisé |

Freinage LDAP : il compte **par compte et par source**. Trois échecs de
`svc_keycloak` depuis le poste freinent ce compte depuis l'hôte aussi, un
instant ; l'attendu « pas les autres du site » vaut pour d'autres comptes
(note ajoutée au § 101).

Le certificat LDAPS servi n'était pas celui de la base : `vlt certificate
regenerate ldaps` demande un **redémarrage du core** (la commande le dit). Et
le PEM de Keycloak en pré-prod était un répertoire (TO-DO **227**).

### 2.4 Rien de noté ailleurs

- On se connecte en SSH sous le domaine **principal** (`bob.recette@acme.lan`),
  et il faut le droit `auth` : un groupe commun ne suffit pas, contrairement à
  ce que dit la formation (TO-DO **223**).
- Un refus de `--fetch-key` n'est pas répondu : 10 s d'attente par tentative
  (TO-DO **224**).
- Le NSS de l'agent attribue un UID à tout nom en `<compte>@<domaine>` qu'on lui
  demande (`alice.martin@svc.acme.lan` → 5003) : c'est voulu (`uid_service.go`,
  plafond de 2000), noté pour mémoire.
