13.[FAIT-IA] [UX/SECURITY] -> Message illisible au rejet d'une cle publique deja enregistree
       Symptome : « Erreur ajout clé publique : Erreur ajout clé publique : Error 1062 (23000):
       Duplicate entry 'ssh-rsa AAAAB3...' for key 'unique_pubkey' ».
       L'erreur brute de MySQL remontait telle quelle a l'administrateur, et taisait la seule
       information utile : QUEL compte detient deja la cle.

       La contrainte elle-meme est CORRECTE et conservee (decision validee). unique_pubkey est
       globale, pas par utilisateur, et c'est delibere : l'API authentifie par signature SSH,
       donc une cle partagee entre deux comptes laisserait son porteur choisir son identite a
       chaque requete — le journal n'enregistrerait que le nom qu'il a bien voulu declarer. Et
       revoquer une cle compromise resterait une chasse au lieu d'une operation unique.
       (Contrainte introduite en mars, commit 003c113 — anterieure aux travaux de securite.)

       Corrige :
       - AddUserKey traduit l'erreur 1062 et NOMME le compte qui detient la cle. La recherche
         compare LEFT(public_key, 255), exactement comme l'index : comparer la chaine entiere
         repondrait « aucun » la ou la base vient pourtant de refuser l'insertion.
       - Double prefixe supprime dans web_profil.go, qui reformatait un message deja explicite.
       - Code HTTP 409 au lieu de 500 : une cle deja enregistree est un conflit, pas une panne.
         Et le message part desormais a l'utilisateur, qui voyait « Erreur lors de l'ajout »
         sans savoir quoi corriger.

       Consequence d'exploitation a connaitre : une personne disposant d'un compte courant ET
       d'un compte d'administration doit generer deux cles distinctes.

14.[FAIT-IA] [GPO] -> Ordre d'application repense + 26 nouveaux modules (TO-DO tache 2)
    -1 ORDRE D'APPLICATION. L'ancien ordre etait faux : fichiers en 30, APRES paquets (20) et
       services (21). Un service demarrait donc sur la configuration par defaut du paquet, puis
       la GPO deposait la vraie configuration SANS RIEN RELANCER. La machine tournait avec une
       conf que personne n'avait choisie, jusqu'au prochain redemarrage.
       Nouveau modele en phases, avec bornes constantes (phaseFiles, phaseSources...) pour qu'un
       ajout ne demande jamais de renumeroter :
         10-19 fichiers | 20-29 sources | 30-39 paquets | 40-59 config | 60-69 services
         70-79 menage   | 80+  utilisateur
       Consequence traitee : deposer une conf avant d'installer son paquet cree un conflit de
       conffile. --force-confold + --force-confdef ajoutes cote apt, sans quoi le comportement
       dependrait de la distribution et de son mode interactif.

    -2 CATALOGUE PORTE DE 8 A 34 MODULES. Seul mount_hardening reste volontairement de cote.
       Groupes A (sauf mount_hardening), B, C et D de la TO-DO livres integralement :
       serveur (schema, cle d'etat, identite), agent (appliqueur), et regles de restriction.
       3 nouveaux champs dynamiques avec leur peuplement : kernel_module_policy/module,
       user_shell/shell, user_group_membership/group.

    -3 GARDE-FOUS SUR LES MODULES CAPABLES DE RENDRE UNE MACHINE INJOIGNABLE.
       Choix valide : verification + retour arriere automatique.
       - pam_policy n'ecrit JAMAIS dans /etc/pam.d/ (piles = ordre d'instructions, une erreur
         casse l'auth ; le projet en a deja fait l'experience sur /etc/pam.d/login). Uniquement
         pwquality.conf.d/ et faillock.conf, qui sont des fichiers de PARAMETRES.
         Refuse un verrouillage sans deverrouillage automatique. even_deny_root = no : sinon N
         echecs volontaires sur root suppriment le dernier acces de secours.
       - boot_params regenere ET valide GRUB avant installation, restaure sinon.
       - selinux_mode refuse enforcing sur un systeme jamais reetiquete (etiquettes manquantes
         -> sshd ne demarre plus -> machine injoignable, donc incorrigeable a distance).
       - local_account_policy exclut root et uid < 1000 par construction, mode report_only par
         defaut qui liste sans modifier.

    -4 file_retention est le SEUL module qui detruit des donnees. Quatre garde-fous bloquants :
       regles de chemin des Restrictions, motif sans separateur, age minimal d'un jour verifie
       cote serveur ET agent, liens symboliques jamais suivis, un seul niveau de recursion.

    -5 POINT DE VIGILANCE LIVRE EN BASE : la liste des groupes locaux attribuables
       (user_group_membership) ne contient QUE des groupes de peripheriques. docker, lxd, kvm,
       libvirt, disk, adm, shadow, sudo et wheel en sont deliberement absents : chacun permet
       directement ou non de lire ou modifier n'importe quel fichier — appartenir a docker revient
       a etre root, puisqu'on peut monter / dans un conteneur. Les ajouter reste possible depuis
       l'interface, mais c'est alors une decision explicite d'un membre du groupe vaultaire.

    -6 user_git_config n'accepte qu'une LISTE FERMEE de cles. git permet de definir des commandes
       executees automatiquement (core.pager, alias, filtres, hooks) : un champ libre donnerait
       une execution de code arbitraire dans le contexte de l'utilisateur, a chaque commande git.
