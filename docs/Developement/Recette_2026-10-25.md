## 3. Ce que dit le rapport

### 3.1 La version déclarée des agents Linux est fausse — cause trouvée

`vlt agent` affiche pour les deux postes Linux :

```
debian-clone           A83fznlYSplh-22-10-2026  illisible : remult,remult,root
localhost.localdomain  svmAFOFVMs2n-25-10-2026  illisible : alice@acme.lan
WIN-9GN5L91KPQL        nPIK5c2rfeDL-22-10-2026  2.3.0
```

La « version » est la liste des **sessions ouvertes**. L'inventaire `02_12`
compte une ligne de trop : `GetCPUCount` rend la sortie de `nproc` avec son
retour à la ligne, et tout ce qui suit glisse d'un cran. Windows n'a pas le
défaut. Les Linux sont donc « ⚠ inconnue » pour `vlt agent`, alors que la mise
à jour marche : après `vlt agent target 2.3.0`, le poste rend « 2.3.0 installe :
déjà en place ». Correction d'une ligne, dans le SDK : TO-DO **214**.

Autres lignes de `vlt agent` :

- `default` (`snLabpG5YHsz-14-10-2026`) : « jamais déclarée » — une machine
  créée le 14/10 et jamais raccordée, à supprimer si elle ne sert pas.
- Le nom d'hôte du poste de recette est `localhost.localdomain` : c'est ce que
  verront l'inventaire, le portail et les journaux. `hostnamectl set-hostname`
  sur le poste.

### 3.2 L'ouverture de session SSH, avant et après la mise à jour

Détail dans `Analyse_ouverture_session_ssh_2026-10-14.md`, § 5.1. En bref :

| | Agent du 11/10 (`gfadbd12`) | Agent à jour |
|---|---|---|
| `--fetch-key` lancés par sshd | 2 (1,7 s et 3,0 s) | **0** |
| `restorecon -RF` sur tout le dossier | 2 (2,2 s et 3,2 s) | 0 — `-F ~` et `-RF ~/.ssh`, 0,3 s |
| `gpasswd` / `usermod` à chaque connexion | oui | non |
| de la première commande Vaultaire au shell | 10,1 s | **4,4 s** |

- Le **188** est fermé par le 197 : la clé est dans `authorized_keys` — sshd ne
  lance plus `--fetch-key` pour la trouver (TO-DO **213** fermé).
- Chaque `--fetch-key` de l'ancien agent lançait `who`, `free -h`, `nproc` et
  `os-release` : l'inventaire de la session qu'il ouvrait. Noté au **196**.
- `time vaultaire_client --fetch-key` à la main : 1,32 s (le 196 l'annonçait
  à 1,2 s au moins).
- Côté client : clé ED25519 acceptée (« partial success »), puis
  keyboard-interactive — mot de passe, puis « Code a 6 chiffres (0000 si vous
  n'en avez pas) » —, puis le shell. La bannière SSH (« GOUGOUGAGA ») s'affiche
  **avant** l'authentification, comme prévu.
- Il reste ≈ 3,6 s après la dernière commande de Vaultaire : la fin du cycle
  GPO de compte et la phase session du système. Le journal des connexions
  (`vlt_client-Debug-connexions.log`, mode debug) les découpera.
